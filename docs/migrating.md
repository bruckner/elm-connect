# Migrating from 0.1 to 0.2

0.2 changes how a call is sent. A config record becomes a client built
from a protocol, the codec a call is generated with is part of its
type, and a method no longer holds its descriptor. Generated code
changes with it, so code generated by 0.1 does not compile against the
0.2 runtime.

In short:

1. Upgrade the runtime and the binary together, and regenerate
   ([Regenerating](#regenerating)).
2. Replace each `Rpc.Config` with an `Rpc.Client`
   ([The client and the protocol](#the-client-and-the-protocol)).
3. Add the codec to the annotations that name `Rpc.Call`
   ([The codec in the type](#the-codec-in-the-type)).
4. Rename what the application calls in `Proto.Json`, now
   `Proto.Json.Encode` and `Proto.Json.Decode`
   ([The JSON codecs](#the-json-codecs)).
5. Follow the compiler through the rest: the pure halves, traces and
   any method written by hand.

The release notes ([CHANGELOG.md](../CHANGELOG.md)) list every change,
including those that need no edit.

## The client and the protocol

In 0.1 a call was sent with a config, a record whose fields an
application set with record update syntax:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-client
config : Rpc.Config
config =
    let
        base =
            Rpc.config "https://api.example.com"
    in
    { base
        | transport =
            Rpc.Transport.connectGet
                |> Rpc.Transport.withMaxGetUrl 2048
        , headers = [ ( "X-Api-Key", "key-7" ) ]
        , timeout = Just 10000
        , retry = Just (Rpc.Retry.on [ Rpc.Code.Unavailable ])
    }
```

In 0.2 it is sent with a client, built from a protocol and a base URL,
and adjusted with `Rpc.Client`'s modifiers:

```elm examples/notes/elm/src/Snippets/Migrating.elm#client
client : Rpc.Client Rpc.Json
client =
    Rpc.client
        (Rpc.Protocol.connect
            |> Rpc.Protocol.withConnectGet
            |> Rpc.Protocol.withMaxGetUrl 2048
        )
        "https://api.example.com"
        |> Rpc.Client.withHeaders [ ( "X-Api-Key", "key-7" ) ]
        |> Rpc.Client.withTimeout 10000
        |> Rpc.Client.withRetry (Rpc.Retry.on [ Rpc.Code.Unavailable ])
```

| 0.1 | 0.2 |
|---|---|
| `Rpc.Config` | `Rpc.Client Rpc.Json` ([The codec in the type](#the-codec-in-the-type)) |
| `Rpc.config url` | `Rpc.client Rpc.Protocol.connect url` |
| `transport = t` | `Rpc.client`'s first argument |
| `headers = hs` | `Rpc.Client.withHeaders hs` |
| `timeout = Just ms` | `Rpc.Client.withTimeout ms` |
| `withCredentials = True` | `Rpc.Client.withCredentials` |
| `retry = Just policy` | `Rpc.Client.withRetry policy` |
| `cfg.baseUrl`, `cfg.headers`, … | `Rpc.Client.baseUrl client`, `headers`, `timeout`, `credentials`, `retry`, `protocol` |
| `Rpc.checkConfig cfg` | none: a bad base URL or header fails the call unsent, its `Rpc.Error.cause` `BadCall`, and a size limit below 1 is no limit ([When a client cannot send](calling.md#when-a-client-cannot-send)) |

A client holds its protocol's functions, so it lives in code rather
than in a message. Where 0.1 kept a config in the model and updated its
headers, keep the state the headers come from and build the client
where calls are sent:

```elm examples/notes/elm/src/Snippets/Migrating.elm#client-for
clientFor : { token : String } -> Rpc.Client Rpc.Json
clientFor session =
    Rpc.client Rpc.Protocol.connect "https://api.example.com"
        |> Rpc.Client.withHeaders [ ( "Authorization", "Bearer " ++ session.token ) ]
```

Clients built alike are still `==`, and `Rpc.Client.toJson` gives a
client as data for logs and tests.

`Rpc.Transport` is now `Rpc.Protocol`:

| 0.1 | 0.2 |
|---|---|
| `Rpc.Transport.Transport` | `Rpc.Protocol.Protocol Rpc.Json` |
| `Rpc.Transport.connect` | `Rpc.Protocol.connect` |
| `Rpc.Transport.connectGet` | `Rpc.Protocol.connect \|> Rpc.Protocol.withConnectGet` |
| `Rpc.Transport.transcode` | `Rpc.Protocol.transcode` |
| `Rpc.Transport.withMaxGetUrl`, `withReadMaxBytes`, `withWriteMaxBytes`, `name` | the same names in `Rpc.Protocol` |

`withConnectGet` and `withMaxGetUrl` leave a protocol other than
Connect as it is. `Rpc.Protocol.codec` and `Rpc.Protocol.toJson` are
new.

Two protocols are new, both over protobuf binary, and both send the code
generated by default (`codec=both`) or with `codec=binary`
([The generator](#the-generator)): `Rpc.Protocol.connectBinary`, Connect
over its binary codec, and `Rpc.Protocol.grpcWeb`, gRPC-Web
([calling.md](calling.md#protocols)). A build of `main` before 0.2
wrote `connectBinary` as `Rpc.Transport.connect |>
Rpc.Transport.withCodec Rpc.Transport.Proto`.

## The codec in the type

A call, a client and a protocol carry their codec as their first type
parameter, `Rpc.Json` or `Rpc.Binary`. Code generated with the default,
`codec=both`, gives calls free in the codec, which a client of either
sends; `codec=json` gives `Rpc.Call Rpc.Json` calls, proto3 JSON alone as
0.1's were; and `codec=binary` gives `Rpc.Call Rpc.Binary`. An annotation that named
`Rpc.Call req res` gains the parameter: `Rpc.Call Rpc.Json req res`
for one codec, or a variable shared with the client for a function over
any call.

A build of `main` before 0.2 named the binary format otherwise, and
none of these names is kept: `Rpc.Proto` and `Proto.Codec.Proto` are
`Rpc.Binary` and `Proto.Codec.Binary`, `Rpc.Protocol.connectProto` is
`connectBinary`, `Proto.Method.initProto` is `initBinary`, the
generated `encodeNoteBytes`, `decodeNoteBytes`, `mergeNoteBytes` and
`mergeNestedNoteBytes` are `encodeNoteBinary`, `decodeNoteBinary`,
`mergeNoteBinary` and `mergeNestedNoteBinary`, and the generator option
`wire=both|json|proto` (CLI `--wire`) is `codec=both|json|binary`
(CLI `--codec`).

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-fetch
fetch : Rpc.Config -> (Result Rpc.Error res -> msg) -> Rpc.Call req res -> Cmd msg
fetch cfg toMsg call =
    call
        |> Rpc.Call.withTimeout 10000
        |> Rpc.send cfg toMsg
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#fetch
fetch : Rpc.Client codec -> (Result Rpc.Error res -> msg) -> Rpc.Call codec req res -> Cmd msg
fetch rpcClient toMsg call =
    call
        |> Rpc.Call.withTimeout 10000
        |> Rpc.send rpcClient toMsg
```

A client sending a call generated without its codec is a compile error.
A build of `main` before 0.2 failed that call at run time with
`Rpc.Error.MissingCodec`, which is gone. What reads a call's JSON or
picks its binding takes a JSON call: `Rpc.Call.viaBinding`,
`requestJson` and `toJson`, and `Proto.Method.encodeRequest` and
`responseDecoder` of a method. A call generated under `codec=both`, the
default, is pinned to `Rpc.Json` where one of them is applied, as a call
of 0.1's always was. A helper that took one call and both sent it over binary and
read its JSON now takes two: a generated call is free in the codec at each
use, a function's argument is not.

## The pure halves

`Rpc.request` and `Rpc.taskFromRequest` take the client where they took
the config. `Rpc.request` gives a `Result Rpc.Error Rpc.Request`: the
error for a call sending would refuse (a base URL with a query, a path
value its template cannot match, a header a request cannot carry, a
request over the write limit, a request value with no proto3 JSON),
where 0.1 built a request for any call. Code that rewrites a request
becomes a `case`, `Ok request -> … |> Rpc.taskFromRequest client call`
and `Err error -> Task.fail error`, and a test of a request reads it
with `Result.map`. `Rpc.response` takes an `Rpc.Client Rpc.Json` and a JSON
call, as before. An answer to a binary call, read by elm/http as bytes,
goes to `Rpc.responseBytes` with an `Rpc.Client Rpc.Binary`
([calling.md](calling.md#the-pure-halves)).

## Traces

`Rpc.Trace.transport` is replaced by `Rpc.Trace.protocol` and
`Rpc.Trace.codec`, and `Rpc.Trace.procedure` gives the Connect path:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-trace
describe : Rpc.Trace.Trace -> String
describe trace =
    Rpc.Trace.transport trace
        ++ " "
        ++ Rpc.Trace.serviceName trace
        ++ "/"
        ++ Rpc.Trace.methodName trace
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#trace
describe : Rpc.Trace.Trace -> String
describe trace =
    -- "connect json /notes.v1.NotesService/GetNote"
    Rpc.Trace.protocol trace
        ++ " "
        ++ Rpc.Trace.codec trace
        ++ " "
        ++ Rpc.Trace.procedure trace
```

`Rpc.Trace.toJson` writes `"protocol"` and `"codec"` where it wrote
`"transport"`, and adds `"procedure"` beside `"service"` and
`"method"`, as `Rpc.Call.toJson` does. A log query that read
`transport` reads `protocol`.

## Methods written by hand

Generated code needs no edit beyond regenerating. A method written by
hand changes builders. In 0.1 a method took its codecs and a
descriptor:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-method
getNote : Notes.V1.GetNoteRequest -> Rpc.Call Notes.V1.GetNoteRequest Notes.V1.Note
getNote =
    Rpc.call
        (Proto.Method.method Notes.V1.encodeGetNoteRequest
            Notes.V1.decodeNote
            (Proto.Method.descriptor "notes.v1.NotesService"
                "GetNote"
                Proto.Method.IdempotencyNoSideEffects
                "notes.v1.GetNoteRequest"
                "notes.v1.Note"
                [ getNoteBinding ]
            )
        )
```

where the binding was `Proto.Http` data:

```elm examples/notes/elm/src/Snippets/Migrating.elm#binding
getNoteBinding : Proto.Http.Binding
getNoteBinding =
    -- GET /v1/{name=notes/*}
    Proto.Http.binding
        { method = "GET"
        , path =
            [ Proto.Http.literal "v1"
            , Proto.Http.variable
                { fieldPath = [ Notes.V1.GetNoteRequest.name ]
                , template = [ Proto.Http.literal "notes", Proto.Http.wildcard ]
                }
            ]
        , customVerb = Nothing
        , body = Proto.Http.noBody
        , responseBody = Nothing
        , query = []
        }
```

In 0.2 it takes the service's full name and the method's name first,
then its codecs, and modifiers set the rest:

```elm examples/notes/elm/src/Snippets/Migrating.elm#method
getNote : Notes.V1.GetNoteRequest -> Rpc.Call Rpc.Json Notes.V1.GetNoteRequest Notes.V1.Note
getNote =
    Rpc.call
        (Proto.Method.initJson "notes.v1.NotesService"
            "GetNote"
            Notes.V1.encodeGetNoteRequest
            Notes.V1.decodeNoteWith
            |> Proto.Method.withIdempotency Proto.Method.IdempotencyNoSideEffects
            |> Proto.Method.withRoutes [ routeGetNote ]
        )
```

Its route for transcoding is a function of the typed request, as
generated code writes one, rather than the binding as data:

```elm examples/notes/elm/src/Snippets/Migrating.elm#route
routeGetNote : Notes.V1.GetNoteRequest -> Proto.Route.Route
routeGetNote request =
    -- GET /v1/{name=notes/*}
    { method = "GET"
    , path = "v1/" ++ Proto.Route.segments request.name
    , query = []
    , body = Nothing
    , invalid = Proto.Route.checkSegments "name" [ "notes", "*" ] request.name
    }
```

- `Proto.Method.initJson` builds a method with JSON codecs,
  `Proto.Method.initBinary` one with binary codecs, and
  `Proto.Method.init` one with both. A method's type gains its codec,
  `Proto.Method.Method codec req res`.
- A method's idempotency is `IdempotencyUnknown` unless
  `Proto.Method.withIdempotency` sets it.
- `Proto.Method.withRoutes` gives the routes for transcoding, one
  function per binding (`Proto.Method.withJsonRoutes` for routes that
  also read the request's JSON), and `Proto.Method.withResponseBody n
  "field"` names the field binding `n`'s answer is read from, for a rule
  with a `response_body`. A method that is never transcoded needs
  neither. `Proto.Http` bindings are the descriptor's data alone: no
  call is built from them.
- `Proto.Method.toDescriptor` is gone: a method no longer holds a
  descriptor. Build one with `Proto.Method.descriptor` where the data is
  needed.

`Rpc.Call.descriptor` is gone too. A call's method is read by
`Rpc.Call.serviceName`, `methodName` and `idempotency`, as before, and
by the new `Rpc.Call.procedure`:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-procedure
procedure : Rpc.Call req res -> String
procedure call =
    let
        descriptor =
            Rpc.Call.descriptor call
    in
    "/" ++ Proto.Method.service descriptor ++ "/" ++ Proto.Method.name descriptor
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#procedure
procedure : Rpc.Call codec req res -> String
procedure call =
    -- "/notes.v1.NotesService/GetNote"
    Rpc.Call.procedure call
```

For a generated method's full descriptor, its types and its bindings,
name the generated value, `Notes.V1.NotesService.descriptorGetNote`.
Transcoding reads the route functions rather than the descriptor's
bindings, so the call no longer holds the descriptor, and a program
that does not name it carries none.

## Descriptors

0.1's `Proto.Registry` held the descriptors by full name. In 0.2 they
are `Proto.Descriptors`, with the same functions (`empty`, `fromDescriptors`,
`union`, `message`, `enum`, `messages`, `enums`) but `wellKnown`, which is
`Proto.WellKnown.descriptors`, and each generated package module's
`registry` is `descriptors`. 0.1 code:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-note-fields
noteFields : List String
noteFields =
    Proto.Registry.message "notes.v1.Note" Notes.V1.registry
        |> Maybe.map (Proto.Message.fields >> List.map Proto.Field.name)
        |> Maybe.withDefault []
```

and in 0.2:

```elm examples/notes/elm/src/Snippets/Migrating.elm#note-fields
noteFields : List String
noteFields =
    Proto.Descriptors.message "notes.v1.Note" Notes.V1.descriptors
        |> Maybe.map (Proto.Message.fields >> List.map Proto.Field.name)
        |> Maybe.withDefault []
```

`Proto.Any.describe` takes the `Descriptors`. A descriptor's full name
is `Proto.Message.fullName` and `Proto.Enum.fullName`, where 0.1 had
`typeName`, which is now a message's typed value's
(`Proto.Message.typeName : Message a -> String`).

## Errors

`Rpc.Error.Error` is no longer a union to match. It is read through
functions, in three layers: the RPC (`code`, `message`, `details`,
`source`); the HTTP exchange underneath, `cause`, which is elm/http's
error with the answer kept, and `httpStatus`; and the codec under that,
`protoError` ([calling.md](calling.md#errors)). `Reason` and
`StatusError` are gone. Code that read `Rpc.Error.code` and
`Rpc.Error.message` is unchanged.

| 0.1 | 0.2 |
|---|---|
| `RpcStatus status answer` | `cause` is `BadStatus answer`, `source` is `Just status.source`; `status.code`, `status.message` are `code error`, `message error`; `status.details` is `details error` |
| `HttpStatus answer` | `cause` is `BadStatus answer` and `source` is `Nothing`; for a 2xx that is not the protocol's answer, `BadResponse answer`, code `Unknown` |
| `BadResponse problem answer` | `cause` is `BadResponse answer`; a body that did not decode has `message` `bad response body` and its problem in `protoError` |
| `NoAnswer Timeout` | `cause` is `Timeout` |
| `NoAnswer NetworkError` | `cause` is `NetworkError` |
| `NoAnswer (BadUrl url)`, `NoAnswer (InvalidHeader name)`, `NoAnswer (RequestTooLarge _)` | `cause` is `BadCall`; `message` says which, without the URL or the header's value |
| `NoAnswer (ResponseTooLarge _)` | `cause` is `BadResponse answer`, the answer's status and headers kept, its body dropped |
| `Rpc.Error.details error : List Any` | `Rpc.Error.details error : List (Result Proto.Error.Error Any)` (below) |

An application coming from elm/http reads `cause` as the `Http.Error` it
had:

| elm/http | `Rpc.Error.cause` |
|---|---|
| `Http.BadUrl _` | `BadCall` |
| `Http.Timeout` | `Timeout` |
| `Http.NetworkError` | `NetworkError` |
| `Http.BadStatus n` | `BadStatus answer`, with `answer.statusCode == n`, which can be 200 (below) |
| `Http.BadBody _` | `BadResponse answer` |

Over gRPC-Web a failure is stated in the trailers of a 200, so a reader that branches on `answer.statusCode` should not assume a failing status there; `code` is the reading for it.

A `case` on `cause` matches a status where 0.1 matched a constructor:

```elm examples/notes/elm/src/Snippets/Migrating.elm#errors
retryable : Rpc.Error -> Bool
retryable error =
    case Rpc.Error.cause error of
        Rpc.Error.BadStatus answer ->
            List.member answer.statusCode [ 502, 503, 504 ]

        Rpc.Error.NetworkError ->
            True

        Rpc.Error.Timeout ->
            True

        Rpc.Error.BadCall ->
            False

        Rpc.Error.BadResponse _ ->
            False
```

- Codes are as before, the client's own included: a timeout is
  `DeadlineExceeded`, a network failure `Unavailable`, a request over
  its limit `ResourceExhausted`. Those codes, and the ones inferred from
  a bare HTTP status, have server meanings too: code that acts on a code
  the server stated checks `Rpc.Error.source error /= Nothing`.
- Messages hold no value from the request or the answer: a bad URL is
  `bad URL: the base URL holds a query or a fragment` or `bad URL: the
  browser could not read it`, and a body that did not decode `bad
  response body`. `Rpc.Error.protoError error |> Maybe.map
  Proto.Error.toString` is the decoder's full text, which can quote the
  answer's data.
- A `BadCall` or a `BadResponse` is never retried, whatever a policy's
  codes: a request over its write limit, retried in 0.1 under
  `ResourceExhausted`, is not.
- Tests and previews build errors with `Rpc.Error.fromCode`,
  `fromStatus`, `fromResponse`, `timeout`, `networkError`, `badCall`,
  `badAny`, `badResponse` and `badBody`, and they are `==` to the
  runtime's when they state the same things.

## Any, the registry and error details

An `Any` holds its message's protobuf binary, as in protobuf's own
runtimes, whatever codec the calls use. In 0.1 it held the message's
JSON.

- `Proto.Any.unpack : Message a -> Any -> Maybe a` gives the value, or
  `Nothing` for another type or binary that is not the message;
  `tryUnpack` gives `Result Proto.Error.Error a` with why. 0.1's
  `unpack` gave `Maybe (Result Problem a)`, and its `Problem` was `Json`
  or `BinaryOnly`; `Proto.Any.Problem` is gone, and the proto layer has
  one error type, `Proto.Error.Error`: `TypeMismatch { expected,
  actual }` for another type, `BadBinary` for binary that is not the
  message (where, and why), `UnregisteredType url` for a type a registry
  lacks, `BadJson` for JSON that is not the message.
  `Proto.Error.toString` describes one for a log. `bytes` reads the
  binary and `toJson registry` its proto3 JSON, failing with
  `UnregisteredType` or `BadBinary`, of a nested `Any` named by its own
  type.
- Proto3 JSON of an `Any` goes through a registry: `Proto.Json.Decode.anyWith
  registry` replaces `any`, and a message holding an `Any` is written
  with `Proto.Json.Encode.encodeWith registry`, where 0.1 had `encodeAny`.
  An `"@type"` the registry lacks fails the read, naming the URL, and
  the write gives `UnregisteredType`, as protojson does; 0.1 kept such
  an `Any` as JSON. `Proto.Registry.lenient` makes a registry keep it as
  JSON again, with no binary (`Proto.Any.bytes` is a `Maybe`), written as
  protobuf binary as its type URL alone.
- A message's typed value holds its full name and both codecs:
  `Proto.Message.init "notes.v1.Note" encodeNote decodeNote
  encodeNoteBinary decodeNoteBinary` (`initWith` for one that reaches an
  `Any`) replaces 0.1's `Proto.Message.message encode decoder default
  descriptor`, and the readers `encode`, `decoder`, `default` and
  `toDescriptor` are gone: use the generated codecs, `defaultNote` and
  `Notes.V1.Note.descriptor`.
- A generated message that reaches an `Any` has `decodeNoteWith`, which
  takes the registry, in place of `decodeNote`.
- A generated encoder gives a `Proto.Json.Encode.Encoder`, not a
  `Json.Encode.Value`: `Proto.Json.Encode.encodeTotal (encodeNote note)` writes
  one that nothing it holds can refuse, as `encodeNote note` did, and
  `Proto.Json.Encode.encode` or `encodeWith registry` one that can (a message
  holding an `Any`, a `Timestamp`, `Duration`, `FieldMask`, `Struct`,
  `Value` or `ListValue`), giving a `Result`: a value proto3 JSON has no
  form for is refused with `Proto.Error.BadValue`, where 0.1 wrote it.
- A call over JSON whose request holds such a value is not sent, over
  Connect and over every transcoding binding, path and query included:
  it fails with `Rpc.Error.badValue`'s `BadCall`, code
  `InvalidArgument`, where 0.1 sent the value as it wrote it. Over
  binary it is sent.
- `Proto.Registry` is the table: each generated package's `registry`
  holds its own messages, `Proto.WellKnown.registry` the well-known
  types and `Proto.ErrorDetails.registry` `google.rpc`'s error details;
  `register`, `union` and `unionAll` compose them. Give the client the
  one its `Any`s need with `Rpc.Client.withRegistry`; a JSON client whose
  messages hold an `Any` needs one, and a request whose `Any` it cannot
  write fails unsent, a `BadCall` whose `Rpc.Error.protoError` is the
  `Proto.Error.Error` the write gave.
- A method holds no registry: a hand-written method's JSON codecs take
  the client's (`Proto.Method.initJson "notes.v1.NotesService" "GetNote"
  encodeGetNoteRequest (\_ -> decodeNote)`); a hand-written encoder `f :
  a -> Json.Encode.Value` is given as `Proto.Json.Encode.succeed << f`.
  `Proto.Method.encodeRequest`, `responseDecoder`, `Rpc.Call.requestJson`
  and `Rpc.Call.toJson` take a registry, and the first, third and fourth
  give a `Result`.
- `Rpc.Error.details` is `List (Result Proto.Error.Error
  Proto.Any.Any)`: each detail, or why it could not be read
  (`UnregisteredType url` for a `google.rpc.Status` body's detail of a
  type the client's registry lacks; `BadJson` for a detail that is not
  one, `BadBinary` for a `grpc-status-details-bin` that does not decode).
  Unpack one with `Proto.Any.unpack` and the type's typed value,
  `Proto.ErrorDetails.badRequest` for `google.rpc.BadRequest`
  ([descriptors.md](descriptors.md#error-details)).

## Value, Struct and ListValue

A `google.protobuf.Value` is a `Proto.Value.Value`, a union of JSON's six
kinds, where 0.1 held elm/json's `Json.Encode.Value`. A `Struct` field is
`Maybe (Dict String Proto.Value.Value)` and a `ListValue` field `Maybe
(List Proto.Value.Value)`. elm/json's `==` walked only the left value's
keys, so `{"a":1}` was equal to `{"a":1,"b":2}`, and so was any message
holding them; the union's `==` compares content. Its reads are bounded
by the depth limit ([calling.md](calling.md#nesting-depth)).

Code that read a member with elm/json and built one with `Json.Encode`:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-extra
color : Notes.V1.Note -> Maybe String
color note =
    note.extra
        |> Maybe.andThen (Dict.get "color")
        |> Maybe.andThen (Json.Decode.decodeValue Json.Decode.string >> Result.toMaybe)


withColor : String -> Notes.V1.Note -> Notes.V1.Note
withColor c note =
    { note | extra = Just (Dict.insert "color" (Json.Encode.string c) (Maybe.withDefault Dict.empty note.extra)) }


extraJson : Notes.V1.Note -> Json.Encode.Value
extraJson note =
    Json.Encode.dict identity identity (Maybe.withDefault Dict.empty note.extra)
```

matches on the kinds and builds them with the constructors, and goes
through `Proto.Value.toJson` (and `fromJson`, the other way) to hand one
to a port or to its own decoders, or reads one in its own decoders with
`Proto.Value.decoder`:

```elm examples/notes/elm/src/Snippets/Migrating.elm#extra
color : Notes.V1.Note -> Maybe String
color note =
    case note.extra |> Maybe.andThen (Dict.get "color") of
        Just (ValueString c) ->
            Just c

        _ ->
            Nothing


withColor : String -> Notes.V1.Note -> Notes.V1.Note
withColor c note =
    { note | extra = Just (Dict.insert "color" (ValueString c) (Maybe.withDefault Dict.empty note.extra)) }


extraJson : Notes.V1.Note -> Json.Encode.Value
extraJson note =
    Proto.Value.toJson (ValueStruct (Maybe.withDefault Dict.empty note.extra))
```

A singular `Value` field stays a `Maybe`: `Nothing` is absent, and the
JSON `null` is `Just ValueNull` where it was `Just Json.Encode.null`.

## Durations

`Proto.Duration`'s names follow elm/time's (`millisToPosix`), and
`toString` gives a `Maybe`:

| 0.1 | 0.2 |
|---|---|
| `Proto.Duration.fromMilliseconds` | `Proto.Duration.fromMillis` |
| `Proto.Duration.toMilliseconds` | `Proto.Duration.toMillis` |
| `Proto.Duration.toString d : String` | `Proto.Duration.toString d : Maybe String`, `Nothing` for a duration that is not valid |

Every duration the application builds, and every one read from proto3
JSON, is valid, so `toString` of one gives `Just`. A duration read from
protobuf binary is held as the peer wrote it, which may not be valid
(`Proto.Duration.isValid`); 0.1 had no binary codec. A proto3 JSON
write refuses one that is not valid, with `Proto.Error.BadValue`.
`normalize` gives a duration's normal form. To sort durations or key a
`Dict` by them, use the fields `toSecondsAndNanos` gives.

## Timestamps

A `google.protobuf.Timestamp` was a `Time.Posix`, which counts
milliseconds, so digits past the third were dropped. It is now
`Proto.Timestamp.Timestamp`, exact to the nanosecond: a field is
`Maybe Proto.Timestamp.Timestamp` (`Proto.Timestamp.Timestamp` in a
list, map or oneof). Convert at the edges with `toPosix` and
`fromPosix`:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-timestamps
createdText : Time.Zone -> Notes.V1.Note -> String
createdText zone note =
    case note.createTime of
        Just posix ->
            clock zone posix

        Nothing ->
            ""


touch : Time.Posix -> Notes.V1.Note -> Notes.V1.Note
touch now note =
    { note | updateTime = Just now }


newestFirst : List Notes.V1.Note -> List Notes.V1.Note
newestFirst =
    List.sortBy (.updateTime >> Maybe.map Time.posixToMillis >> Maybe.withDefault 0)
        >> List.reverse


byInstant : List Notes.V1.Note -> Dict.Dict String Notes.V1.Note
byInstant notes =
    notes
        |> List.filterMap (\note -> Maybe.map (\t -> ( String.fromInt (Time.posixToMillis t), note )) note.createTime)
        |> Dict.fromList
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#timestamps
createdText : Time.Zone -> Notes.V1.Note -> String
createdText zone note =
    case note.createTime of
        Just created ->
            clock zone (Proto.Timestamp.toPosix created)

        Nothing ->
            ""


touch : Time.Posix -> Notes.V1.Note -> Notes.V1.Note
touch now note =
    { note | updateTime = Just (Proto.Timestamp.fromPosix now) }


newestFirst : List Notes.V1.Note -> List Notes.V1.Note
newestFirst =
    List.sortBy (.updateTime >> Maybe.map instantKey >> Maybe.withDefault ( 0, 0 ))
        >> List.reverse


byInstant : List Notes.V1.Note -> Dict.Dict ( Int, Int ) Notes.V1.Note
byInstant notes =
    notes
        |> List.filterMap (\note -> Maybe.map (\t -> ( instantKey t, note )) note.createTime)
        |> Dict.fromList


instantKey : Proto.Timestamp.Timestamp -> ( Int, Int )
instantKey timestamp =
    let
        parts =
            Proto.Timestamp.toSecondsAndNanos timestamp
    in
    ( parts.seconds, parts.nanos )
```

`clock` stands for an application's own helper. A `Time.Posix` was not
`comparable`; a timestamp is not either, and its text does not sort
chronologically (0, 3, 6 or 9 fractional digits, so `…:45Z` sorts after
`…:45.5Z`). Sort and key by the fields `toSecondsAndNanos` gives, as
`instantKey` does: for valid timestamps they order as the instants do.
The package gives no order or key of its own, since one has to say what
a timestamp that is not valid means.

| 0.1 | 0.2 |
|---|---|
| `Maybe Time.Posix` field | `Maybe Proto.Timestamp.Timestamp` field |
| `Proto.Timestamp.fromString s : Maybe Time.Posix` | `Proto.Timestamp.fromString s : Maybe Proto.Timestamp.Timestamp`, every digit kept |
| `Proto.Timestamp.toString t : String` | `Proto.Timestamp.toString t : Maybe String`, `Nothing` for a timestamp that is not valid; 0, 3, 6 or 9 fractional digits |
| `Time.now` for a field | `Proto.Timestamp.now`, or `Proto.Timestamp.fromPosix` of a `Time.Posix` |
| `Time.posixToMillis` to compare or key | the fields of `Proto.Timestamp.toSecondsAndNanos`, or `Time.posixToMillis` of `toPosix` to the millisecond |

`fromPosix` clamps a `Time.Posix` outside years 1 to 9999 to that
range; `toPosix` drops the nanoseconds past the millisecond, toward
the past.
Every timestamp the application builds, and every one read from proto3
JSON, is valid, so `toString` of one gives `Just`. A timestamp read
from protobuf binary is held as the peer wrote it, which may not be
valid (`Proto.Timestamp.isValid`); a proto3 JSON write refuses one that
is not valid, with `Proto.Error.BadValue`, and `normalize` gives its
normal form.

## The JSON codecs

`Proto.Json` is gone: its encoders are in `Proto.Json.Encode` and its
decoders in `Proto.Json.Decode`, as elm/json splits `Json.Encode` and
`Json.Decode`. Generated code calls them, so most applications meet the
change only in what they call themselves: running a generated encoder
(`Proto.Json.Encode.encodeTotal`, `encode`, `encodeWith`) and
`Proto.Json.Encode.succeed` for an encoder written by hand. Some names
match elm/json's (`Proto.Json.Encode.object`, `Proto.Json.Decode.float`),
and every reference is written qualified.

An encoder's name says what it gives. A checked encoder, which can
refuse a value, is a bare noun (`object`, `optional`, `timestamp`); a
plain field encoder, giving `Maybe Json.Encode.Value`, begins with
`plain` or `implicit`; one that unwraps a message encoder that cannot
refuse begins with `total`; a value encoder is named after the decoder
it mirrors (`int64`, `bytes`). The decoder of a `double` field is
`Proto.Json.Decode.double`, and of a `float` field `Proto.Json.Decode.float`,
as `Proto.Binary` names them: 0.1's `Proto.Json.float`, which read a
`double`, is `Proto.Json.Decode.double`, not `Proto.Json.Decode.float`.

## The generator

- A `google.protobuf.Duration` field is written
  `Proto.Duration.Duration`, qualified, as `Proto.Any.Any` and
  `Proto.Value.Value` are, and generated modules no longer import
  `Proto.Duration exposing (Duration)`. A message named `Duration`
  beside a `Duration` field generates without a `rename`.
- A `google.protobuf.Timestamp` field is `Proto.Timestamp.Timestamp`,
  written qualified, where it was `Time.Posix`
  ([Timestamps](#timestamps)), and generated modules no longer import
  `Time`.
- Every message gets both codecs, proto3 JSON and protobuf binary, its
  typed value and its package's `registry`, whatever the options say.
  The new option `codec` says which codec each method's calls are typed
  at, the `codec` of `Rpc.Call codec req res`: by default `both`, so a
  call goes to a client of either codec; `codec=json` (CLI
  `--codec json`) proto3 JSON alone, as 0.1's were; or `codec=binary`
  (CLI `--codec binary`) protobuf binary alone. 0.1 had no such option,
  so a 0.1 buf or protoc configuration needs no change for it: code that
  sends every call over JSON compiles under the default, and `json` is
  the opt-in that narrows the calls' types and leaves the binary codecs
  behind them out of the bundle. Write it as `codec`, with the values
  `both`, `json` and `binary`: pre-release builds of 0.2 called it
  `wire`, with `proto` for `binary`, and neither spelling is accepted.
- Each `google.api.http` binding gets a generated route function in its
  service's module (`routeGetNote0`), and a request message whose
  bindings put fields in the query gets a query encoder in its
  package's module (`queryOfListNotesRequest`). They are new names: a
  method named for one (`RouteGetNote0` beside `GetNote`) is
  `naming::value_collision`, and a `rename` resolves it. Under
  `codec=binary` a method gets no routes, since transcoding takes JSON.

## Regenerating

Generated code names the runtime release it was generated for, and
0.2's runtime exposes `Proto.Version.v0_2` alone, and no `Proto.Json`.
Code generated by 0.1 against the 0.2 runtime stops with:

```text
-- MODULE NOT FOUND ------------------------------------- generated/Greet/V1.elm

You are trying to import a `Proto.Json` module:

10| import Proto.Json
           ^^^^^^^^^^
I checked the "dependencies" and "source-directories" listed in your elm.json,
but I cannot find it! Maybe it is a typo for one of these names?

    Proto.Enum
    Proto.Error
    Proto.Bytes
    Proto.Field
```

and, in a module that imports no JSON codecs, with the naming error for
`Proto.Version.v0_1` that [install.md](install.md#versions) shows.

Regenerate with the 0.2 binary, with the options used before.
`elm-connect check` reports modules generated by another release.
Before 1.0 every minor release may change generated code, so regenerate
with each one ([install.md](install.md#versions)).

## Also

- A Connect error body whose code is missing, `null` or a name the
  protocol does not define takes the HTTP status's code, as connect-go
  and connect-es read it: one with a string `message` and no code, which
  0.1 read as an `HttpStatus` error, now states a status, `source`
  `Just ConnectBody`, with the body's message, and an unknown name reads
  as the status's code, not `Unknown`.
- `Rpc.Call.withRetry` and `Rpc.Call.withoutRetry` set one call's retry
  policy, and `Rpc.Retry.withDeadline` and `Rpc.Retry.next` are new
  ([calling.md](calling.md#retries)). `next` is given the failed call's
  `Rpc.Error.Error` and reads its code itself.
- Decoding is stricter where proto3 JSON says so: an out-of-range
  `double` or `float`, a lowercase `t` or `z` in a timestamp, an `Any`
  without a type URL, a field mask path with `_` and a string holding
  a lone surrogate now fail to decode.
- `Proto.Binary.decode` gives `Result Proto.Error.Binary a`: the
  message, the reason, the fields and the byte offset of a failure. A
  build of `main` before 0.2 gave `Maybe a`; `Result.toMaybe` keeps code
  written for it, and `Proto.Error.toString (Proto.Error.BadBinary
  problem)` describes the failure for a log. `Proto.Binary.merge` takes
  the message's full name first, as generated code passes it, and a
  `string` field whose bytes are not UTF-8 now fails to decode.
