# Migrating from 0.1 to 0.2

0.2 changes how a call is sent. A config record becomes a client built
from a protocol, the codec a call is generated with is part of its
type, and a method no longer holds its descriptor. Generated code
changes with it, so code generated by 0.1 does not compile against the
0.2 runtime.

In short:

1. Upgrade the runtime and the binary together, and regenerate
   ([Regenerating](#regenerating)).
2. Replace each `Rpc.Config` with an `Rpc.Client`
   ([The client and the protocol](#the-client-and-the-protocol)).
3. Add the codec to the annotations that name `Rpc.Call`
   ([The codec in the type](#the-codec-in-the-type)).
4. Follow the compiler through the rest: the pure halves, traces and
   any method written by hand.

The release notes ([CHANGELOG.md](../CHANGELOG.md)) list every change,
including those that need no edit.

## The client and the protocol

In 0.1 a call was sent with a config, a record whose fields an
application set with record update syntax:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-client
config : Rpc.Config
config =
    let
        base =
            Rpc.config "https://api.example.com"
    in
    { base
        | transport =
            Rpc.Transport.connectGet
                |> Rpc.Transport.withMaxGetUrl 2048
        , headers = [ ( "X-Api-Key", "key-7" ) ]
        , timeout = Just 10000
        , retry = Just (Rpc.Retry.on [ Rpc.Code.Unavailable ])
    }
```

In 0.2 it is sent with a client, built from a protocol and a base URL,
and adjusted with `Rpc.Client`'s modifiers:

```elm examples/notes/elm/src/Snippets/Migrating.elm#client
client : Rpc.Client Rpc.Json
client =
    Rpc.client
        (Rpc.Protocol.connect
            |> Rpc.Protocol.withConnectGet
            |> Rpc.Protocol.withMaxGetUrl 2048
        )
        "https://api.example.com"
        |> Rpc.Client.withHeaders [ ( "X-Api-Key", "key-7" ) ]
        |> Rpc.Client.withTimeout 10000
        |> Rpc.Client.withRetry (Rpc.Retry.on [ Rpc.Code.Unavailable ])
```

| 0.1 | 0.2 |
|---|---|
| `Rpc.Config` | `Rpc.Client Rpc.Json` ([The codec in the type](#the-codec-in-the-type)) |
| `Rpc.config url` | `Rpc.client Rpc.Protocol.connect url` |
| `transport = t` | `Rpc.client`'s first argument |
| `headers = hs` | `Rpc.Client.withHeaders hs` |
| `timeout = Just ms` | `Rpc.Client.withTimeout ms` |
| `withCredentials = True` | `Rpc.Client.withCredentials` |
| `retry = Just policy` | `Rpc.Client.withRetry policy` |
| `cfg.baseUrl`, `cfg.headers`, … | `Rpc.Client.baseUrl client`, `headers`, `timeout`, `credentials`, `retry`, `protocol` |
| `Rpc.checkConfig cfg` | `Rpc.Client.problems client` |

A client holds its protocol's functions, so it lives in code rather
than in a message. Where 0.1 kept a config in the model and updated its
headers, keep the state the headers come from and build the client
where calls are sent:

```elm examples/notes/elm/src/Snippets/Migrating.elm#client-for
clientFor : { token : String } -> Rpc.Client Rpc.Json
clientFor session =
    Rpc.client Rpc.Protocol.connect "https://api.example.com"
        |> Rpc.Client.withHeaders [ ( "Authorization", "Bearer " ++ session.token ) ]
```

Clients built alike are still `==`, and `Rpc.Client.toJson` gives a
client as data for logs and tests.

`Rpc.Transport` is now `Rpc.Protocol`:

| 0.1 | 0.2 |
|---|---|
| `Rpc.Transport.Transport` | `Rpc.Protocol.Protocol Rpc.Json` |
| `Rpc.Transport.connect` | `Rpc.Protocol.connect` |
| `Rpc.Transport.connectGet` | `Rpc.Protocol.connect \|> Rpc.Protocol.withConnectGet` |
| `Rpc.Transport.transcode` | `Rpc.Protocol.transcode` |
| `Rpc.Transport.withMaxGetUrl`, `withReadMaxBytes`, `withWriteMaxBytes`, `name` | the same names in `Rpc.Protocol` |

`withConnectGet` and `withMaxGetUrl` leave a protocol other than
Connect as it is. `Rpc.Protocol.codec` and `Rpc.Protocol.toJson` are
new.

Two protocols are new, both over protobuf binary and both needing code
generated with `codec=proto` or `codec=both`
([The generator](#the-generator)): `Rpc.Protocol.connectProto`, Connect
over its proto codec, and `Rpc.Protocol.grpcWeb`, gRPC-Web
([calling.md](calling.md#protocols)). A build of `main` before 0.2
wrote `connectProto` as `Rpc.Transport.connect |>
Rpc.Transport.withCodec Rpc.Transport.Proto`.

## The codec in the type

A call, a client and a protocol carry their codec as their first type
parameter, `Rpc.Json` or `Rpc.Proto`. Code generated with `codec=json`,
the default, gives `Rpc.Call Rpc.Json` calls; `codec=proto` gives
`Rpc.Call Rpc.Proto`; and `codec=both` gives calls free in the codec,
which a client of either sends. An annotation that named
`Rpc.Call req res` gains the parameter: `Rpc.Call Rpc.Json req res`
for one codec, or a variable shared with the client for a function over
any call.

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-fetch
fetch : Rpc.Config -> (Result Rpc.Error res -> msg) -> Rpc.Call req res -> Cmd msg
fetch cfg toMsg call =
    call
        |> Rpc.Call.withTimeout 10000
        |> Rpc.send cfg toMsg
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#fetch
fetch : Rpc.Client codec -> (Result Rpc.Error res -> msg) -> Rpc.Call codec req res -> Cmd msg
fetch rpcClient toMsg call =
    call
        |> Rpc.Call.withTimeout 10000
        |> Rpc.send rpcClient toMsg
```

A client sending a call generated without its codec is a compile error.
A build of `main` before 0.2 failed that call at run time with
`Rpc.Error.MissingCodec`, which is gone.

## The pure halves

`Rpc.request` and `Rpc.taskFromRequest` take the client where they took
the config. `Rpc.response` takes an `Rpc.Client Rpc.Json` and a JSON
call, as before. An answer to a binary call, read by elm/http as bytes,
goes to `Rpc.responseBytes` with an `Rpc.Client Rpc.Proto`
([calling.md](calling.md#the-pure-halves)).

## Traces

`Rpc.Trace.transport` is replaced by `Rpc.Trace.protocol` and
`Rpc.Trace.codec`, and `Rpc.Trace.procedure` gives the Connect path:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-trace
describe : Rpc.Trace.Trace -> String
describe trace =
    Rpc.Trace.transport trace
        ++ " "
        ++ Rpc.Trace.serviceName trace
        ++ "/"
        ++ Rpc.Trace.methodName trace
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#trace
describe : Rpc.Trace.Trace -> String
describe trace =
    -- "connect json /notes.v1.NotesService/GetNote"
    Rpc.Trace.protocol trace
        ++ " "
        ++ Rpc.Trace.codec trace
        ++ " "
        ++ Rpc.Trace.procedure trace
```

`Rpc.Trace.toJson` writes `"protocol"` and `"codec"` where it wrote
`"transport"`, and adds `"procedure"` beside `"service"` and
`"method"`, as `Rpc.Call.toJson` does. A log query that read
`transport` reads `protocol`.

## Methods written by hand

Generated code needs no edit beyond regenerating. A method written by
hand changes builders. In 0.1 a method took its codecs and a
descriptor:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-method
getNote : Notes.V1.GetNoteRequest -> Rpc.Call Notes.V1.GetNoteRequest Notes.V1.Note
getNote =
    Rpc.call
        (Proto.Method.method Notes.V1.encodeGetNoteRequest
            Notes.V1.decodeNote
            (Proto.Method.descriptor "notes.v1.NotesService"
                "GetNote"
                Proto.Method.IdempotencyNoSideEffects
                "notes.v1.GetNoteRequest"
                "notes.v1.Note"
                [ getNoteBinding ]
            )
        )
```

In 0.2 it takes the service's full name and the method's name first,
then its codecs, and modifiers set the rest:

```elm examples/notes/elm/src/Snippets/Migrating.elm#method
getNote : Notes.V1.GetNoteRequest -> Rpc.Call Rpc.Json Notes.V1.GetNoteRequest Notes.V1.Note
getNote =
    Rpc.call
        (Proto.Method.json "notes.v1.NotesService"
            "GetNote"
            Notes.V1.encodeGetNoteRequest
            Notes.V1.decodeNote
            |> Proto.Method.withIdempotency Proto.Method.IdempotencyNoSideEffects
            |> Proto.Method.withBindings [ getNoteBinding ]
        )
```

The binding is the same `Proto.Http` value in both:

```elm examples/notes/elm/src/Snippets/Migrating.elm#binding
getNoteBinding : Proto.Http.Binding
getNoteBinding =
    -- GET /v1/{name=notes/*}
    Proto.Http.binding
        { method = "GET"
        , path =
            [ Proto.Http.literal "v1"
            , Proto.Http.variable
                { fieldPath = [ Notes.V1.GetNoteRequest.name ]
                , template = [ Proto.Http.literal "notes", Proto.Http.wildcard ]
                }
            ]
        , customVerb = Nothing
        , body = Proto.Http.noBody
        , responseBody = Nothing
        , query = []
        }
```

- `Proto.Method.json` builds a method with JSON codecs,
  `Proto.Method.proto` one with binary codecs, and
  `Proto.Method.both` one with both. A method's type gains its codec,
  `Proto.Method.Method codec req res`.
- A method's idempotency is `IdempotencyUnknown` unless
  `Proto.Method.withIdempotency` sets it.
- `Proto.Method.withBindings` gives the routes for transcoding as
  `Proto.Http` bindings, read from the request's JSON. Generated code
  uses `Proto.Method.withRoutes` instead, with a generated route
  function per binding. A method that is never transcoded needs
  neither.
- `Proto.Method.toDescriptor` is gone: a method no longer holds a
  descriptor. Build one with `Proto.Method.descriptor` where the data is
  needed.

`Rpc.Call.descriptor` is gone too. A call's method is read by
`Rpc.Call.serviceName`, `methodName` and `idempotency`, as before, and
by the new `Rpc.Call.procedure`:

```elm examples/notes/elm/src/Snippets/Migrating.elm#before-procedure
procedure : Rpc.Call req res -> String
procedure call =
    let
        descriptor =
            Rpc.Call.descriptor call
    in
    "/" ++ Proto.Method.service descriptor ++ "/" ++ Proto.Method.name descriptor
```

```elm examples/notes/elm/src/Snippets/Migrating.elm#procedure
procedure : Rpc.Call codec req res -> String
procedure call =
    -- "/notes.v1.NotesService/GetNote"
    Rpc.Call.procedure call
```

For a generated method's full descriptor, its types and its bindings,
name the generated value, `Notes.V1.NotesService.descriptorGetNote`.
Transcoding reads the route functions rather than the descriptor's
bindings, so the call no longer holds the descriptor, and a program
that does not name it carries none.

## The generator

- `codec=proto` (CLI `--codec proto`) generates the protobuf binary
  codecs alone, and `codec=both` adds them beside the JSON ones. The
  default, `codec=json`, generates JSON codecs alone, as 0.1 did. A
  build of `main` before 0.2 named the binary codecs alone
  `codec=binary`, which is now refused with `options::unknown_option`:
  "The option `codec` is `binary`, which is now spelled `proto`."
- Each `google.api.http` binding gets a generated route function in its
  service's module (`routeGetNote0`), and a request message whose
  bindings put fields in the query gets a query encoder in its
  package's module (`queryOfListNotesRequest`). They are new names: a
  method named for one (`RouteGetNote0` beside `GetNote`) is
  `naming::value_collision`, and a `rename` resolves it. Under
  `codec=proto` a method gets no routes, since transcoding takes JSON.
- `Proto.Any.pack` of a message generated under `codec=proto` holds its
  binary alone. A build of `main` before 0.2 held a `null` JSON beside
  it.

## Regenerating

Generated code names the runtime release it was generated for, and
0.2's runtime exposes `Proto.Version.v0_2` alone. Code generated by 0.1
against the 0.2 runtime stops with:

```text
-- NAMING ERROR ----------------------------------------- generated/Greet/V1.elm

I cannot find a `Proto.Version.v0_1` variable:

20|     Proto.Version.v0_1
        ^^^^^^^^^^^^^^^^^^
The `Proto.Version` module does not expose a `v0_1` variable. These names seem
close though:

    Proto.Version.v0_2
    Proto.Json.any
    Proto.Json.enum
    Proto.Json.int32
```

Regenerate with the 0.2 binary, with the options used before.
`elm-connect check` reports modules generated by another release.
Before 1.0 every minor release may change generated code, so regenerate
with each one ([install.md](install.md#versions)).

## Also

- `Rpc.Error.Reason` has a new constructor, `InvalidPathValue { field,
  template }`: a transcoded call whose path value its template cannot
  match is not sent. A `case` on `Reason` needs the branch.
- `Rpc.Call.withRetry` and `Rpc.Call.withoutRetry` set one call's retry
  policy, and `Rpc.Retry.withDeadline` and `Rpc.Retry.next` are new
  ([calling.md](calling.md#retries)).
- Decoding is stricter where proto3 JSON says so: an out-of-range
  `double` or `float`, a lowercase `t` or `z` in a timestamp, an `Any`
  without a type URL, a field mask path with `_` and a string holding
  a lone surrogate now fail to decode.
