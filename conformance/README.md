# Conformance

The conformance corpus pins what the generator emits (`docs/design.md`
§7). Each case is a directory under `cases/`:

```
cases/<case>/
  options.txt            optional: the generator's options, as a protoc
                         plugin parameter on one line (`int64=int`)
  input/                 .proto files; all of them are compiled and generated
  include/               optional: .proto files the input may import, which
                         are compiled but not requested
  expected/
    <Module/Path>.elm    the Elm generated from the input, one file per module
    warnings.txt         beside the modules, when generating warns: the
                         warnings (`streaming=skip`'s skipped methods)
  or
    diagnostics.txt      the problems generating reports instead
```

A case expects either modules or `diagnostics.txt`, never both. Inputs are
compiled with protox, with `input/` and `include/` as the include paths,
and every file under `input/` is requested; nothing under `include/` is.
A requested package is generated whole (design §3.1), so an `include/`
file of a requested package is in its module (`packages_whole` case);
one of any other package is not generated. Without `options.txt` a
case is generated with the default options; an `options.txt` with
problems (`options::*`) is not generated at all, and its problems are the
case's `diagnostics.txt`.

## The checks

`crates/elm-connect-gen/tests/conformance.rs` runs four tests over every
case; `just check` runs them with the other Rust tests.

- **golden**: regenerating each modules case gives exactly its expected
  files, byte for byte but for the version on the header line (below),
  none missing and none extra, and warns exactly
  its `warnings.txt`, rendered as `diagnostics.txt` is, or not at all
  when it has none. A failure shows a unified diff. A unit test in the
  same file exercises the warnings' mismatch and blessing paths.
- **diagnostics**: generating each `diagnostics.txt` case fails, and the
  problems, rendered narrow (80 columns, no colour) with the proto sources
  attached, are exactly `diagnostics.txt`. A unit test in the same file
  also exercises the mismatch and blessing paths on a throwaway case.
- **compiles**: every case's expected modules compile with `elm make` in
  `harness/`, an Elm application whose source directories are the runtime
  package's `../../src` and a scratch `generated/` (gitignored) the test
  copies the modules into. Cases compile one at a time, since two cases may
  define the same module.
- **formatted**: `elm-format --validate` accepts every expected module.

The tests use the pinned compiler, Elm 0.19.2. `compile-with.sh` runs the
compiles check, and builds the runtime package, with another one:

```sh
conformance/compile-with.sh path/to/elm   # or: just compile-with path/to/elm
```

CI runs it with Elm 0.19.0 and 0.19.1 (design §8).

## Blessing

Blessing accepts the generator's current output as the expected output:

```sh
just bless
```

runs the golden and diagnostics tests with `ELM_CONNECT_BLESS=1`, which
rewrites each case's `expected/` (adding, replacing and deleting modules
and `warnings.txt`, or rewriting `diagnostics.txt`) instead of comparing. Read the diff before
committing it: the blessed output is what users will maintain against.

Generated code names the generator's version on its first line,
`-- Generated by elm-connect 0.1.0 from ...`, which is provenance, in
the doc comments' links to the runtime's source at the release, and in
`elmConnectVersion_`, which names the release's major and minor
(`Proto.Version.v0_1`) and is code the compiles check builds against
the runtime (design §8). The expected modules carry a placeholder for
the patch on the header line, `-- Generated by elm-connect 0.1.X from
...`, and in those links (`.../blob/0.1.X/src/Proto/Any.elm`): the
golden test puts it in place of the version before comparing,
and blessing writes it, so a patch release leaves the corpus alone. A
minor or major release still re-blesses every expected module, for the
header's minor and the `elmConnectVersion_` line. The route replay's
modules in `tests/Routes` (below) carry the same placeholder. The
other committed generated code keeps the real version: the notes
example's, which is what a user sees, and the conformance suite's
under `live/suite/elm`, which the plugin writes through buf.

To add a case, create `cases/<name>/input/` with its protos and bless. For
a case that is meant to fail, create an empty `expected/diagnostics.txt`
first, then bless.

## Route fixtures

`routes/` pins what HTTP request a request becomes under a
`google.api.http` rule (design §7). `routes/routes.proto` declares the
request messages and one service whose methods carry the rules (all but
one, which has none); each `routes/*.json` file holds fixtures:

```json
{
  "name": "fields outside the path become query parameters",
  "method": "routes.v1.Routes.GetMessage",
  "binding": 2,
  "rule": { "verb": "GET", "template": "/v1/messages/{message_id}", "body": "" },
  "request": { "messageId": "123456", "revision": "2", "sub": { "subfield": "foo" } },
  "expect": {
    "path": "/v1/messages/123456",
    "query": [["revision", "2"], ["sub.subfield", "foo"]],
    "body": null
  }
}
```

`binding` is `0` for the rule's own and `n` for its `n`th additional
binding; `rule` repeats that binding so the file reads without the proto.
A method without a rule has `"binding": null` and `"rule": null`, and
expects the implicit route: `POST /<package>.<Service>/<Method>` with
the request as its body and `Connect-Protocol-Version: 1`, which
grpc-gateway (`generate_unbound_methods`), Envoy (`auto_mapping`) and a
Connect handler serve (`implicit.json`; the live suite below runs it
against the example server, where the Connect handler mounted beside
Vanguard answers it). `request` is proto3 JSON. `path`
(custom verb included) and the query pairs are as sent,
percent-encoded; `headers`, optional and `[]` when absent, are those
the route itself adds; `body` is JSON or `null` for none.
Bodies compare after dropping `null`s and default values, which a writer
may omit or spell out; the fixtures write them as the generated encoders
and the Rust reference do, defaults left out. Nothing in a fixture is specific to this client,
so a server-side implementation can check itself against the same file.

`crates/elm-connect-gen/tests/routes.rs` holds both ends to them:

- the rule each fixture names is the binding the generator reads, and a
  reference implementation over protobuf's own model of the request
  (prost-reflect's proto3 JSON parser and field presence) turns the
  generated route and the request into the expectation;
- the modules generated from `routes.proto` (`tests/Routes/V1.elm` and
  the service's `tests/Routes/V1/Routes.elm`) and the fixtures as Elm
  data (`tests/RouteFixtures.elm`) are pinned in the runtime's tests,
  where `tests/RouteFixturesTest.elm` replays each through `Rpc.request`
  with the Transcode transport, applying the generated function of the
  fixture's method and choosing its binding with `Rpc.Call.viaBinding`; a
  fixture naming a binding the method lacks fails. `just bless` rewrites
  all three, and the route properties below.

To add a fixture, add it to a `routes/*.json` file (and a method to
`routes.proto` if no rule fits), check that the reference agrees, and
bless. `just live` then runs it against Vanguard ("The route fixtures,
live", below); a change to `routes.proto` is regenerated by `just
live-gen`.

## Route properties

The fixtures are chosen by hand; the route properties are sampled. The
same test file samples requests for every binding of every method of
`routes/routes.proto` (and the implicit route of the method without a
rule) from a fixed seed: strings with what a URL, JSON or an Elm literal
must escape, integers at their bounds and past 2^53, floats' special
values, messages unset and set but empty, repeated and map fields,
wrappers at their defaults, timestamps (to the millisecond, which
`Time.Posix` holds), durations and field masks. Each request's JSON is
written by prost-reflect, usually without defaults and sometimes with
them or under proto field names. The reference gives each one's HTTP
request, and the samples are pinned as Elm data in
`tests/RouteProperties.elm`, which `tests/RoutePropertiesTest.elm`
replays as the fixtures are replayed; another test checks that
prost-reflect reads each sample's JSON back as the message it was
written from. The seed and the number per route (`SEED`, `PER_ROUTE`)
are constants in the test; changing either re-samples every request,
and `just bless` rewrites the file. A float in a path or query is
expected in ECMAScript's Number-to-String form (`1e+21`), which the
runtime sends; a server parses any form proto3 JSON allows. The samples
are not run against the live server.

The runtime's own laws, independent of the reference, are Elm fuzz
tests: `tests/Proto/JsonFuzzTest.elm` (the proto3 JSON codecs, and the
generated codecs of `routes.proto` leaving out defaults) and
`tests/RpcFuzzTest.elm` (`Rpc.request` over Transcode), with their
fuzzers in `tests/Fuzzers.elm`; `just check` runs them with the other
Elm tests.

## Codec round trips

The corpus's expected modules are compiled and diffed but never run; the
codec round trips run them. `codec/codec.proto`, with `codec/other.proto`
for a reference across packages, declares one small message per construct
the generated proto3 JSON codecs handle and one that nests them all.
`crates/elm-connect-gen/tests/codec.rs`:

- samples every message from a fixed seed, with the route properties'
  sampler (`tests/common/sample.rs`), and adds a sample per oneof member
  and ten of the scalars and wrappers at their bounds and special values;
- has prost-reflect write each sample in three forms: canonical
  (defaults left out), with every default written, and under proto names
  with an unknown field added to every message object; another test
  checks that prost-reflect reads each form back as the sample, and
  another that the samples hold every construct the layer is for;
- writes the samples as Elm data, with what the generated encoders must
  write back after decoding each form (`Generated.Codec.Data`, and
  `Generated.Codec.DataInt64Int` with 64-bit values within ±(2^53 − 1)
  for `int64=int`), the modules generated from the protos under the
  default options, `int64=int`, `enum_unknown=zero` and `bytes=bytes`
  (module prefix `Generated.Codec.<Set>`), and a table of each set's
  codecs (`Generated.Codec.Codecs`), all under `tests/Generated/Codec/`.

That tree is gitignored and generated at test time, as the harness's
`generated/` is: the test writes it on every run, `just codec-gen` runs
just that test, and `just elm-check` depends on it. There is nothing to
bless. The generator's output already shows in review through the
corpus, and the fixed seed makes the samples the same each run; the
hand-written Elm (`tests/Codec/RoundTrip.elm` and `RoundTripTest.elm`)
is all that is committed under `tests/Codec/`.

`tests/Codec/RoundTripTest.elm` decodes every form with the generated
decoder of each option set, re-encodes it with the generated encoder, and
compares the JSON with the expected structurally, numbers by value; then
it checks what each option changes. What the encoders must write is
prost-reflect's canonical form but for the differences the design allows,
listed in `allowed_differences` in the Rust test: a float without
presence received as `-0` is written as `0`, and a singular `Empty` field
is always written as `{}`. An `Any`'s packed message is written back as it
arrived.

The binary codecs run against the same samples. The test also writes each
sample's protobuf binary (hex, `binary` in the data modules), deterministic
where prost-reflect's is not: fields in number order, a map's entries in
the order of the Elm `Dict` holding them, every singular `Empty` set, every
`Any`'s packed message re-encoded the same way and a kind-less `Value` given
`null_value`; another test checks that prost-reflect reads each back as
the sample. It generates the protos under `codec=both` (with `int64=int`
and with `bytes=bytes`) and `codec=binary` too, and
`tests/Codec/BinaryRoundTripTest.elm` decodes each sample's binary with the
generated decoder and re-encodes it to the same bytes, with unknown fields
of every wire type appended and without; where the set has JSON codecs, it
checks that the value read from binary writes the JSON the value read from
JSON writes (an `Any` read from binary holds its message's binary, so it
is written in Connect's error-detail form, `binaryJson` in the data), and
that the value read from JSON encodes to the same bytes, but where it
holds an `Any`, which the binary encoder writes with its type URL alone.
Since the encoders write prost-reflect's bytes exactly, prost-reflect reads
what they write. The corpus case `codec_both` is these protos under
`codec=both`, blessed like any other.

For a deeper run, set the number of samples per message (8 by default)
when generating, then run the Elm tests; the next plain run writes the
default samples back:

```sh
ELM_CONNECT_CODEC_SAMPLES=50 cargo test -p elm-connect-gen --test codec
elm-test-rs
```

A sample that fails is a finding. prost-reflect cannot write a
`DoubleValue` or `FloatValue` holding NaN or an infinity (it writes
`null`) or an `Any` without a type URL, so those are not sampled.

## Live verification

The corpus and the fixtures pin what is generated and what request a
call becomes; `live/` runs the runtime against a server (design §7,
live verification):

```
live/
  elm.json            an application: the runtime's ../../src, the example's
                      generated Elm (examples/notes/elm/generated), src/
  src/Live.elm        a headless Platform.worker: envelopes in on the
                      `requests` port, results out on `results`
  src/Live/Call.elm   the envelope, and `entry`, which makes a dispatch
                      table's entry from a generated call function and codecs
  src/Live/Notes.elm  the dispatch table of notes.v1.NotesService
  src/Live/Conformance.elm
                      the dispatch table of the Connect conformance suite's
                      ConformanceService (its unary methods)
  src/Live/Routes.elm the dispatch table of routes.v1.Routes (routes/)
  xhr.mjs             an XMLHttpRequest over node:http, the subset elm/http
                      uses, reporting each exchange
  run.mjs             loads build/elm.js; a module (`createRunner`,
                      `runCases`, `mismatches`, `serve`) and a command
  cases/notes.json    the smoke suite
  conformance.mjs     the client under test for the Connect conformance suite
  conformance.yaml    the features the suite tests (what the runtime supports)
  known-failing.txt   the suite's test cases the runtime fails, with reasons
  known-failing-send.txt
                      those it fails too when sent with Rpc.sendTraced
                      (none right now)
  fetch-conformance.sh
                      fetches connectconformance at its pinned release
  suite/              buf.yaml and buf.gen.yaml, the suite's protos
                      (proto/, vendored; README.md: provenance), and the
                      Elm (elm/) and JavaScript (js/) generated from them
  package.json        @bufbuild/protobuf and protoc-gen-es, pinned with
                      package-lock.json
  build/              the compiled program and connectconformance (gitignored)
  cases/transcode.json  error bodies over REST, as sent and as read
  routes.mjs          the route fixtures, live (below)
  known-divergent-vanguard.json
                      where Vanguard and the fixtures part
  known-divergent-gateway.json
                      where grpc-gateway and the fixtures part
  known-divergent-envoy.json
                      where Envoy and the fixtures part
  envoy/envoy.yaml    Envoy's gRPC-JSON transcoder in front of the example
                      server (docs/envoy.md)
  envoy/envoy-version the Envoy release func-e runs
  cases/envoy.json    Envoy's errors in grpc-status headers, and its own answers
  build/              the compiled program (gitignored)
```

```sh
just live                                     # regenerate, build, start the server, run
node conformance/live/run.mjs --server http://127.0.0.1:8080 conformance/live/cases/notes.json
node conformance/live/run.mjs --serve target/live/bin/notes-server --print conformance/live/cases/notes.json
node conformance/live/run.mjs --serve target/live/bin/notes-server --prefix /gateway --transport transcode conformance/live/cases/notes.json
node conformance/live/run.mjs --server http://127.0.0.1:18081 --origin http://127.0.0.1:18080 conformance/live/cases/transcode.json
```

`just live` regenerates the example with buf and fails if the output
differs from what is committed, builds the server (into `target/live/bin`,
under `CARGO_TARGET_DIR` when that is set) and `Live.elm`
(unoptimized), starts the server on a free port and runs the suite.
`--print` prints each result instead of checking it. `--prefix` adds a
path to the server's URL for the cases' `baseUrl`: the server serves
transcoding twice, by Vanguard at its root and by grpc-gateway under
`/gateway`, and `just live` runs the transcoding cases under both, and
under Envoy (below). `--transport` runs only the cases of one
transport; the transcode cases of `notes.json` make the notes they
change, so they run alone. `--origin` names the example server when
`--server` is a proxy in front of it, as Envoy is: `{server}` in a case
(below) then stands for the origin, not the proxy.

An **envelope**, what the runner sends:

```json
{
  "id": "a name for the call",
  "service": "notes.v1.NotesService",
  "method": "GetNote",
  "request": { "name": "notes/welcome" },
  "transport": "connect",
  "config": {
    "baseUrl": "http://127.0.0.1:8080",
    "headers": [["x-echo", "hi"]],
    "timeout": 500,
    "withCredentials": false,
    "useGet": false,
    "maxGetUrl": null,
    "readMaxBytes": null,
    "writeMaxBytes": null,
    "retry": { "attempts": 2, "backoff": 10, "codes": ["unavailable"], "idempotentOnly": false }
  },
  "binding": null,
  "headers": [["x-echo", "from the call"]],
  "rewrite": [],
  "send": "sendTraced",
  "tracker": null,
  "cancelAfterMs": null
}
```

`request` is proto3 JSON (`{}` when absent); `transport` is `connect`,
`transcode` or `grpcweb` (which needs a build with binary codecs); everything in `config` but `baseUrl` is optional, as are
`binding` (applied with `Rpc.Call.viaBinding`), `headers` (the call's
own, `Rpc.Call.withHeaders`, sent after the config's), `send` (`sendTraced`, the
default, `send`, `task`, `halves` or `taskFromRequest`), `rewrite`, `tracker` (`Rpc.Call.withTracker`) and
`cancelAfterMs`. `useGet` and `maxGetUrl` build the Connect transport
(`Rpc.Transport.connectGet`, `withMaxGetUrl`); `readMaxBytes` and
`writeMaxBytes` apply `Rpc.Transport.withReadMaxBytes` and
`withWriteMaxBytes` to either transport. `retry` builds an
`Rpc.Retry` from `codes` and `attempts`, with `backoff` (default 0),
`maxBackoff` (default the runtime's), `idempotentOnly` (default false) and
`jitter` (default false, so a case's waits are the bounds it states).
`halves` sends through the pure halves, as an application
that needs the answer's headers does: `Rpc.request`, `Http.request` with the
answer kept whole, and `Rpc.response`. `taskFromRequest` builds the request
with `Rpc.request`, puts each `[name, value]` of `rewrite` in place of the
header of that name (in any case), or after the headers when there is none,
and sends it with `Rpc.taskFromRequest`, the config's retry policy applying,
as an application that refreshes a token does; its `trace` is `null`, and
`wire` shows the rewritten request on every attempt.

With `cancelAfterMs` the runner cancels the call that many milliseconds
after sending it with `Rpc.cancel`, under the envelope's tracker or, without
one, its `id`. `Rpc.cancel` reports nothing, so the runner records the
cancellation itself, as an application does, and reports whichever outcome
comes first, the result or `{"canceled": true}`; a later one is dropped, so
a call is reported once. Only `send` without a retry policy and `halves` put
the tracker on the request; `sendTraced`, `task`, `taskFromRequest` and
`send` with a retry policy ignore it, so an envelope sending one of those with `cancelAfterMs` is
refused (`{"runner": …}`) rather than reported cancelled while the call runs
on.

A **result**, what comes back:

```json
{
  "id": "a name for the call",
  "result": { "ok": { "name": "notes/welcome" } },
  "trace": {
    "service": "notes.v1.NotesService", "method": "GetNote", "transport": "connect", "binding": null,
    "httpStatus": 200, "headers": { "content-type": "application/json" }, "trailers": {},
    "code": "ok", "attempts": 1, "duration": 4,
    "request": { "method": "POST", "url": "…", "headers": [["Connect-Protocol-Version", "1"]],
                 "body": "{\"name\":\"notes/welcome\"}", "timeout": null, "withCredentials": false }
  },
  "progress": { "sending": 1, "receiving": 1 },
  "wire": [{ "method": "POST", "url": "…", "requestHeaders": [], "body": "…", "timeout": 0,
             "withCredentials": false, "status": 200, "responseHeaders": {},
             "responseBody": "{…}", "outcome": "load" }]
}
```

`result` is one of `{"ok": <response as proto3 JSON>}`, `{"error":
{"code", "message", "details", "source", "response"}}` (the code as
Connect names it, each detail as `Proto.Json.encodeAny` writes it, the
source as `ConnectBody`, `StatusBody`, `GrpcHeaders` or `HttpStatus`
for a code inferred from the status, and `response` the answer the
error was read from: `statusCode`, `statusText` and `body`),
`{"badResponse": {"problem", "response"}}` for a successful answer whose
body did not decode (elm/json's problem, and the answer as above),
`{"noAnswer": "Timeout"}` (or `NetworkError`, `BadUrl <url>`,
`InvalidHeader <name>`, `RequestTooLarge <size> <limit>`,
`ResponseTooLarge <size> <limit>`) for an
`Rpc.Error.NoAnswer`, `{"canceled": true}` for a call
the runner withdrew with `Rpc.cancel`, and `{"runner": <why>}` for an
envelope the runner could not send: one that does not decode, an unknown
method or a binding the method lacks. `trace` is the `Rpc.Trace` as `Rpc.Trace.toJson` writes it
(`error` the code as Connect names it, `null` on success), and `null`
unless sent with `sendTraced`; `response` is the answer's
`{"status", "headers": [[name, value], …]}` as elm/http gives it, and
`null` unless sent with `halves` and answered; `progress` counts a tracker's
events and is present only with one. `wire` is added by `run.mjs`: each
HTTP exchange made during the call, as `xhr.mjs` saw it (`outcome` is
`load`, `error`, `timeout` or `abort`, or `pending` for one still open). Calls run one at a time, so every
exchange belongs to its call.

A **case file** is a JSON array of cases, run in order:

```json
{
  "name": "connect GetNote",
  "note": "optional prose",
  "call": { "service": "…", "method": "…", "request": {}, "transport": "connect", "config": {} },
  "expect": { "result": { "ok": { "name": "notes/welcome" } }, "trace": { "attempts": 1 } },
  "skip": "optional: why the case is not run"
}
```

`call` is an envelope without `id` (the case's name) whose `baseUrl`
defaults to the server's with `--prefix`, `{server}` standing for the
server's without it (or `--origin`) in one given: the canned answers
(`/status/<n>/`, `/grpc-status/<code>/`) are the server's own, under no
transcoder.
`expect` is matched against the result: an object matches when each of
its keys does, other keys ignored; an array element by element, with
the same length; anything else by equality. `{"$match": "<regex>"}`
matches a string the expression finds, `{"$json": …}` a string whose
JSON parse matches, `{"$contains": […]}` an array with a match for each
element, and `{"$absent": true}` a key that is missing or `null`.

To add a service, add its proto to the example (or a new one beside
it), a dispatch table `src/Live/<Service>.elm` listing `entry` per
method, and the table to `tables` in `Live.elm`.

## The Connect conformance suite

`just live-conformance` (part of `just live`) runs the official
[Connect conformance suite](https://github.com/connectrpc/conformance)
against the runtime (design §7, live verification), at v1.0.6:

```sh
just live-conformance
# by hand, from conformance/live once `just live-conformance-gen live-build` has run:
"$(./fetch-conformance.sh)" --mode client --conf conformance.yaml \
  --known-failing @known-failing.txt -- node conformance.mjs --send halves
```

`fetch-conformance.sh` downloads `connectconformance` from the suite's
GitHub release, checks it against the SHA-256 pinned per platform, and
keeps it in `build/`. In client mode it starts its own reference server
(connect-go) and launches `node conformance.mjs`, writing
`ClientCompatRequest` messages to its stdin and reading a
`ClientCompatResponse` for each from its stdout, protobuf binary, each
prefixed by its length as a 4-byte big-endian integer.
`conformance.mjs` decodes each request with the JavaScript protoc-gen-es
generates from the suite's protos (`suite/js/`, through
`@bufbuild/protobuf`), unpacks its one request message from its `Any` to
proto3 JSON, and makes it an envelope for the runner: `host` and `port` as
the `baseUrl`, `request_headers` as `headers`, `timeout_ms` as `timeout`,
`use_get_http_method` as `useGet`, a non-zero `message_receive_limit`
as `readMaxBytes`, and `cancel.after_close_send_ms` as
`cancelAfterMs` (a unary call's request is sent whole, so the count starts
when the call is sent). The other cancel timings, `before_close_send` and
`after_num_responses`, are for streams, which `conformance.yaml` declares
unsupported; a request with one is refused. The runner calls the method through
`Live.Conformance`, whose calls come from the Elm protoc-gen-elm-connect
generates from the same protos (`suite/elm/`, `streaming=skip`), and the
result is translated back: the response's payload, or the error's code,
message and details (a detail that came as JSON is read back from its
`"@type"` form; one that came as protobuf binary only, `{"type",
"value"}`, is forwarded as the `Any`'s bytes as they came), the answer's
headers, and as trailers those prefixed `trailer-`, which is how Connect
sends a unary call's trailers. With `halves` the wrapper splits the
answer's headers itself; with `sendTraced` it reports the `Trace`'s
`headers` and `trailers`, which `Rpc.splitTrailers` has split. Either
way a repeated header is one value, joined with `", "` as elm/http gives
it, which the suite accepts. A call with no answer is reported as an
error: `Timeout` as `deadline_exceeded`, `NetworkError` as `unavailable`,
`RequestTooLarge` and `ResponseTooLarge` as `resource_exhausted`, anything else, and a bad response, as `unknown`; `{"canceled": true}`, the runner's record of a cancel, as `canceled`. What is reported is only what the runtime gives
an application; the runner's `wire` log is never read.

`--send` picks how calls are sent: `halves` (the default) through the pure
halves, or `sendTraced`, both of which give an application the answer's
headers, or `send` or `task`, which give none. `just live-conformance`
runs both `halves` and `sendTraced`.

`conformance.yaml` declares what is tested (the suite's `Features`):
HTTP/1.1, the Connect protocol, the JSON codec, no compression, unary
calls, Connect GET and the receive limit, and no TLS, HTTP/2 or trailers;
that is 40 test cases (v1.0.6's one receive-limit suite is for servers). `known-failing.txt` lists the test cases the runtime fails
however a call is sent (none: all 40 pass through the halves), and
`known-failing-send.txt` those it fails too through `sendTraced` (39
pass: the cancellation case, since the tasks ignore the tracker), each
with the reason and the ways of sending it holds for; the runner requires a listed
case to fail, so the lists cannot go stale. One test case pattern per line
(`*` one name component, `**` any number), `#` starting a comment.
`connectconformance` reads only the first `--known-failing` flag it is
given, so the `sendTraced` run joins the two files in `build/`.

`suite/buf.gen.yaml` generates both from `suite/proto/`, the suite's
protos exported from `buf.build/connectrpc/conformance` at the commit its
v1.0.6 label names (`just protos-refresh` re-exports them), so generation
needs no network;
`just live-conformance-gen` installs the npm packages with `npm ci`,
regenerates, and fails if the output differs from what is committed.
### The route fixtures, live

The example server serves `routes/routes.proto` too
(`examples/notes/routes` links to `routes/`, so buf generates it with
the example), under Vanguard and under grpc-gateway, each method
echoing the request the transcoder decoded: the request itself when the
response is of its type, otherwise the request as proto3 JSON in
`Message.text` or `Resource.display_name`. `routes.mjs` sends every
fixture through the runner (`transport` `transcode`, the fixture's
`binding`, its request) and checks:

- the request: verb, the path and the query pairs exactly as sent
  (percent-encoded, in order), the body as the fixtures' own checks
  compare it (`null`s and defaults dropped; an empty message dropped
  this way is printed as a `note`), and a fixture's `headers`;
- the answer: HTTP 200, and the echo equal to the fixture's request
  once both are normalized as proto3 JSON (fields without presence at
  their default left out, fields with presence kept when set, `null`
  unset, 64-bit integers as strings, enums by name, bytes, durations
  and timestamps in one form); a `HEAD` answer has no body, so there
  the runtime's `ok` must be `{}`;
- the runtime's `ok`, normalized, equal to the echo.

```sh
node conformance/live/routes.mjs --serve target/live/bin/notes-server --known conformance/live/known-divergent-vanguard.json
node conformance/live/routes.mjs --serve target/live/bin/notes-server --prefix /gateway --known conformance/live/known-divergent-gateway.json
node conformance/live/routes.mjs --server http://127.0.0.1:8080
node conformance/live/routes.mjs --server http://127.0.0.1:18081 --known conformance/live/known-divergent-envoy.json
```

Each transcoder has its known-divergent file: Vanguard's
(`known-divergent-vanguard.json`, the default), grpc-gateway's
(`known-divergent-gateway.json`, run with `--prefix /gateway`) and
Envoy's (`known-divergent-envoy.json`, below). Vanguard
will not serve two routes for one verb and path, and
protoc-gen-grpc-gateway will not generate two bindings with one verb and
path template, so the server serves a binding the transcoder refuses on
another under `<prefix>/layer/<n>` (`GET <prefix>/routes/layers` lists
where each binding is), and its fixture runs with that prefix on
`baseUrl`. The file lists those bindings under `servedApart`, which must
equal the server's; under `fixtures` each fixture whose live call
disagrees: the request (`url`), the transcoder's `answer`, a `reading` of
who is right, and `observed`, matched against the result as a case's
`expect` is; and under `probes` requests the runtime does not make (an
unknown query parameter, a verb without a route, `PATCH` without an
update mask), sent with `fetch` as written (`request`: `method`, `path`
under the prefix, `body`), whose `observed` is matched against `{status,
body}`, the body parsed as JSON. The probes are the same in every file and
record where the transcoders answer differently. A listed fixture
passes while that answer holds and its request (verb, path, query, body
and headers) is still the fixture's, so an entry excuses the
transcoder's answer and never the request; it fails once it agrees, until
its entry is removed; a probe fails when its answer changes.

### Envoy

Envoy's gRPC-JSON transcoder is the third transcoder (`docs/envoy.md`
walks through it). `just live-envoy`, part of `just live`, builds the
example's descriptor set with buf, starts the example server and Envoy
1.40.0 (`envoy/envoy-version`) through func-e, which mise pins, with
`envoy/envoy.yaml`: one listener converts gRPC errors to a
`google.rpc.Status` body (`convert_grpc_status: true`), the other leaves
them in `grpc-status` headers, Envoy's default. It runs the transcoding
cases of `notes.json` and `transcode.json` (with `--origin`) and the
route fixtures against the first, and `cases/envoy.json`, the errors in
headers and Envoy's own answers, against the second. Envoy calls the
server over gRPC and answers itself what no method matches
(`reject_unknown_method`, `reject_unknown_query_parameters`), so the
server's own transcoders never answer in its place.

Envoy reads every binding from its descriptor set and serves each it
can at the root, so `known-divergent-envoy.json` has `servedApart`
`null`: `routes.mjs` then runs every fixture at the root and does not
read the server's `routes/layers`. Envoy serves neither binding of a
verb and path registered twice, without a word, and five fixtures are
404 under it; the file records them, and the probes' answers.

func-e fetches Envoy from Tetrate's archive and checks it against the
SHA-256 listed in the same archive's index (`envoy-versions.json`), so
the suite trusts Tetrate's archive and index; the repository pins
func-e's own download by checksum in `mise.lock`, but not Envoy's.
Envoy's project publishes Linux binaries only; the macOS build is
Tetrate's. func-e 1.6.0 sometimes fails a right archive (it hashes only
what its unpacker has read), and then leaves the unpacked binary in
place, unchecked; the Justfile's `envoy-install` removes it and fetches,
checks and unpacks the archive itself, against the same digest. CI
caches `~/.local/share/func-e`, keyed on `envoy-version`.
